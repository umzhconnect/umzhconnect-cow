# Key Custodian

Single-tenant **token broker** and JWK Set publisher for one party's L2
(`private_key_jwt`) client identity.

The container holds the private key and does the OAuth work *behind* it: it signs
the client assertion and runs the `client_credentials` exchange at the auth
server itself, handing callers only the resulting access token. Neither the
private key nor the signed assertion ever leaves the pod — the blast radius of
the key is this one component.

The **same image** runs once per party. It holds *only* its party's private key
and JWK Set, mounted as individual files at fixed paths. Per-party behaviour
comes entirely from env + the mount source — there is no `/token/{party}` path.
**The container is the party.**

This repo deploys a single party, so there is one custodian:

| Compose service | client_id        | kid   |
|-----------------|------------------|-------|
| `key-custodian` | `${L2_CLIENT_ID}`| `l2`  |

(`kid` = the JWK `kid`, which must equal `L2_KID`; the mounted key files are
`keys/l2.{key,jwks.json}`, generated by `keys/gen-keys.sh l2`.)

## Endpoints

| Method + path     | Purpose                                                 |
|-------------------|---------------------------------------------------------|
| `GET  /jwks.json` | Public JWK Set — served verbatim from the mounted file. The party's external APISIX gateway proxies its public `/jwks.json` route here. |
| `POST /token`     | Run the `private_key_jwt` `client_credentials` flow at the auth server and return its token response. Request body (all optional): `{"client_id": "...", "scope": "...", "authorization_details": [...]}` — `client_id` defaults to `CLIENT_ID` (used as `iss`+`sub`+`client_id`), `scope` defaults to `DEFAULT_SCOPE`, `authorization_details` is forwarded as RFC 9396. Response: the AS token response verbatim (`{"access_token": "<JWT>", "token_type": "Bearer", "expires_in": N, ...}`). Every call performs a fresh exchange (token caching is deferred — see `BACKLOG.md`). |
| `GET  /healthz`   | `{"client_id": ..., "kid": ...}` — handy for confirming which instance you hit. |

## Demo posture — DO NOT USE IN PRODUCTION

`/token` has **no authentication**. Any container on the Docker network — and,
because the port is host-exposed for `tests/scripts/get-token.sh` to work, any
process on the developer's machine — can obtain an access token. That's
intentional for the sandbox (transparency over rigour, same posture as the
committed L1 secrets), but a real deployment would gate `/token` with:

- a **workload-identity** token — the caller presents its k8s ServiceAccount
  token (or SPIFFE SVID), which the custodian verifies and maps to an allowed
  `client_id`/scope policy, or
- mutual TLS between the custodian and its callers, or
- HSM/KMS-backed signing (no PEM on disk at all — the signer only holds a
  `sign` capability, not the key bytes).

The README at `services/keys/README.md` carries the same "demo only" framing for
the key material itself.

## Env contract

| Env                 | Default                | Purpose |
|---------------------|------------------------|---------|
| `CLIENT_ID`         | required               | Default `iss`+`sub`+`client_id` (a `/token` call may override per request) |
| `KID`               | required               | JWT header `kid` (must match the only JWK in `JWKS_PATH`) |
| `KEY_PATH`          | `/keys/private.key`    | RSA private key (PEM) |
| `JWKS_PATH`         | `/keys/jwks.json`      | JWK Set file served verbatim |
| `TOKEN_ENDPOINT`    | required               | Assertion `aud` **and** the token endpoint the exchange POSTs to |
| `DEFAULT_SCOPE`     | `""`                   | Scope requested when a `/token` call omits one |
| `ASSERTION_TTL`     | `60`                   | Assertion lifetime in seconds (1..300) |
| `HTTP_TIMEOUT`      | `10`                   | AS request timeout in seconds |
| `TLS_VERIFY`        | `true`                 | Verify the AS TLS cert (`false` for dev self-signed) |
| `PORT`              | `8000`                 | Bind port inside the container |

## Why one container per party (not a singleton)

1. **Trust isolation.** A breach of `key-custodian-placer` does not yield
   fulfiller's signing capability. A singleton custodian would expand the blast
   radius of any compromise to the whole federation.
2. **Maps onto real federation deployments.** In production each hospital runs
   its own custodian on its own infrastructure. Placer never sees fulfiller's
   private key, and vice versa. The per-party model is architecturally honest;
   the singleton model would normalise a trust posture no real deployment
   adopts.
3. **Single-tenant code is shorter.** No `/token/{party}` path parameter, no
   `party → key` map, no "is the caller allowed to sign for this party" check.
4. **Same pattern as the existing APISIX gateways.** Internal/external gateways
   already run as a per-party template; the custodian fits the same shape.

## Callers in this codebase

| Caller                                   | Endpoint used     |
|------------------------------------------|-------------------|
| `apisix-placer-external` (jwks route)    | `GET /jwks.json`  |
| `apisix-fulfiller-external` (jwks route) | `GET /jwks.json`  |
| `tests/scripts/get-token.sh`             | `POST /token`     |

The browser-side flow in `web-app/src/pages/CredentialsPage.tsx` is **intentionally
left untouched** — the in-browser Web Crypto signing is the teaching point on
that page; replacing it with a server call would hide the most interesting part.

## Kubernetes (namespace `key-custodian`)

Manifests: `ns.yaml`, `key-custodian.yaml` (ConfigMaps + Deployment + Service),
`kustomization.yaml`. Deploy with `kubectl apply -k key-custodian/` (or via the
root kustomization / ArgoCD).

The two key files are split by sensitivity:
- **private key** → the `key-custodian-l2` **Secret** (mounted at `/secret`). It is
  gitignored; in production deliver it as a **SealedSecret** — see
  [`SEALED-SECRETS.md`](SEALED-SECRETS.md) for the full GitOps (no-`kubectl`) guide.
- **public JWKS** → the `key-custodian-jwks` **ConfigMap** in `key-custodian.yaml`
  (mounted at `/jwks`). It's public, so it lives in git as plain YAML — paste your
  `keys/l2.jwks.json` in (it must match the private key's `kid`/`n`).

Supply **out of band** (the repo can't hold them):

1. **Image** — key-custodian is built from this folder, not a public image, and
   ArgoCD does not build. Build & push, then set `image` in `key-custodian.yaml`:
   ```bash
   docker build -t <registry>/umzh-key-custodian:<tag> key-custodian/
   docker push  <registry>/umzh-key-custodian:<tag>
   ```
2. **Private key** — generate (`keys/gen-keys.sh l2`) and deliver it. In production,
   seal it (SealedSecret) per [`SEALED-SECRETS.md`](SEALED-SECRETS.md). For a quick
   dev cluster you *can* `kubectl -n key-custodian create secret generic
   key-custodian-l2 --from-file=private.key=keys/l2.key` — but never the real key,
   and never via `kubectl` where you have no cluster access.

Config (`CLIENT_ID`, `KID`, `TOKEN_ENDPOINT`) is in the
`key-custodian-config` ConfigMap. The external gateway reaches the JWK Set via its
`/jwks.json` route — `JWKS_UPSTREAM` (in `clinical-orders/apisix-external.yaml`)
points at `key-custodian.key-custodian.svc.cluster.local:8000`. `/token` is
unauthenticated (demo): keep the Service ClusterIP-only, never ingress-expose it,
and restrict access with a NetworkPolicy.
